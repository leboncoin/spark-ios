# How to Release

## Overview

A new version of Spark iOS **must** be created with the [`/spark-release`](/.claude/skills/spark-release/SKILL.md) Claude Code skill.

Do not create the tag or the GitHub release manually: the skill makes sure the `CHANGELOG.md` is updated **before** the release, so the released commit always contains its own changelog.

## Prerequisites

- [`gh`](https://cli.github.com/) installed and authenticated (`gh auth status`).
- The `main` branch checked out, clean and up to date with `origin/main`.

## Usage

```
/spark-release
```

## Workflow

1. **Version**: the skill gets the latest tag and asks for the new version, following the [versioning rules](CONTRIBUTING.md#versioning) (`X.Y.Z`, no `v` prefix).
2. **Release notes**: the default notes are generated by GitHub (`releases/generate-notes` API):
   ```markdown
   ## What's Changed
   * fix(button): include padding in UIKit button intrinsic content size by @robergro in https://github.com/leboncoin/spark-ios/pull/1128


   **Full Changelog**: https://github.com/leboncoin/spark-ios/compare/2.2.0...2.2.1
   ```
3. **Release title**: a title is proposed as `X.Y.Z - <summary>` (e.g. `2.2.0 - drop iOS 16 support and set iOS 17 as minimum deployment target`).
4. **Changelog**: the [`update-changelog`](script/SCRIPT_UPDATE_CHANGELOG.md) script adds the new version to `CHANGELOG.md`, then the `/spark-changelog` skill writes the final content. The change is committed (`chore(changelog): update for X.Y.Z`) and pushed on `main` with the `/spark-push` skill.
5. **Tag and release**: after a last confirmation, the tag is created on the changelog commit and pushed, then the GitHub release is published with the title and the generated notes.

Every public action (push on `main`, tag, release) is confirmed before being executed.
