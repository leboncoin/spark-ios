## Project Structure

The repository is a single Swift package (`Package.swift` at the root, product name `Spark`) containing four root folders:

| Folder | Product(s) | Role |
|---|---|---|
| `Spark/` | `Spark` | The umbrella target. `@_exported import`s every component, `SparkCommon`, `SparkTheming` and `SparkResources` in `Sources/Core/Import.swift`, so a consumer only needs `import Spark` to get everything. |
| `Modules/` | `SparkCommon`, `SparkTheming`, `SparkComponentXXX`, ... | Every individual package: the shared `Common` code, the `Theming` system, and one folder per UI component under `Modules/Components/` (`Button`, `Chip`, ...). |
| `Resources/` | `SparkResources` | The Spark iconography: the asset catalog, the generated `ImageResource` accessors, and the `Image`/`UIImage` convenience initializers. |
| `Demo/` | `SparkDemo` | The demo application code (`MainView`, per-component demo screens, theming playground) — see [Demo App](#demo-app). |

Each package under `Modules/` (and `Resources/`, `Demo/`, `Spark/`) has its own `README.md` (integration instructions) and `Sources/Core/Documentation.docc/Documentation.md` (DocC reference) — this file only covers the *shared shape* those packages follow, not their individual APIs.

### Modules/Common

`SparkCommon` holds code shared by every component: cross-component protocols, extensions, and helpers. Some of it is only meant for use *within* the Spark team's own repositories, in which case it's marked `@_spi(SI_SPI)` to keep it out of the public API surface seen by consumers of the design system. It ships two extra products for testing: `SparkCommonTesting` (public protocol mocks) and `SparkCommonSnapshotTesting` (shared snapshot-testing helpers).

### Modules/Components/XXX

Every UI component (`Components/Button`, `Components/Chip`, `Components/SelectionControls`, ...) follows the identical internal structure described in [Component Architecture](#component-architecture) below.

## Component Architecture

Every component package under `Modules/Components/XXX/` is structured as:

```
Modules/Components/XXX/
├── Sources/
│   ├── Core/            — production code
│   │   ├── AccessibilityIdentifier/
│   │   ├── Constants/
│   │   ├── Documentation.docc/
│   │   ├── Enum/
│   │   ├── Environment/
│   │   ├── Model/
│   │   ├── Token/
│   │   ├── UseCase/
│   │   ├── View/
│   │   └── ViewModel/
│   └── Testing/         — public mocks for consumers of this component's tests (mostly Sourcery.generated.swift)
└── Tests/
    ├── UnitTests/        — mirrors the Sources/Core structure (Sources/Core/Enum/Intent.swift -> Tests/UnitTests/Enum/IntentTests.swift)
    └── SnapshotTests/    — configuration + scenarios, also generates the images used in Documentation.docc
```

### Sources/Core folders

| Folder | Role |
|---|---|
| **AccessibilityIdentifier** | Public `enum` of `static let` accessibility identifier strings used by the views. Must be documented; the property name must contain `view` or the component's own name. |
| **Constants** | `static let`/`static func` constants used by views and/or use cases. Can contain sub-enums. |
| **Documentation.docc** | The DocC reference (`Documentation.md`) plus the image resources generated by the snapshot tests, surfaced in its "Rendering" section. |
| **Enum** | The enums used to configure the component (e.g. intent, size). A public enum should expose a `default` case. |
| **Environment** | The SwiftUI `EnvironmentValues` for the component: one `@Entry var` (prefixed with the component's name) plus a documented `View` extension (`sparkXXX(...)`) to set it. UIKit doesn't use this folder. |
| **Model** | The `Equatable` value types set by use cases and consumed by views. Token-typed properties (`any ColorToken`, `any TypographyFontToken`) are prefixed accordingly (`tintColorToken`, `titleFontToken`) and always have a default (`.zero`, `.empty`, `ColorTokenClear()`, ...). |
| **Token** | The component's own theme-derived values (colors, spacing, sizes, ...), grouped by category and built from `any Theme`. See [Theming Architecture](#theming-architecture) for how this bridges to the theming system. |
| **UseCase** | The component's business rules: a `protocol` plus a `struct` implementation, generally with a single `execute` function. |
| **View** | The SwiftUI (`SparkXXX`) and UIKit (`SparkUIXXX`) views. UIKit views inherit from `UIView` or `UIControl`. |
| **ViewModel** | A `final class` that holds no business rules itself — it only calls use cases and publishes their results (`@Published private(set) var`) for the views to observe. |

### Build order

New component files are created in this order, since later ones depend on earlier ones:

`Enum` → `Model` → `Token` → `Environment` → `UseCase` → `ViewModel` → `View` → `Tests` → `Documentation`

### Sourcery annotations

[Sourcery](https://github.com/krzysztofzablocki/Sourcery) generates test/mock boilerplate from these markers:

| Annotation | Placed on | Generates |
|---|---|---|
| `// sourcery: AutoMockable` | protocols | A mock conforming to the protocol, for use in tests. |
| `// sourcery: AutoMockable, AutoMockTest` | UseCase protocols | The mock, plus a unit test asserting the mock's default behavior. |
| `// sourcery: AutoPublisherTest, AutoViewModelStub` | ViewModel `final class` | A stub for previews/snapshots, plus publisher-change unit tests. |
| `// sourcery: theme = "Identical"` | a UseCase `execute` parameter, or a ViewModel `@Published` property, of theme/token type | Tells Sourcery to compare that parameter/property by identity rather than by generated equality, since `any Theme`/token existentials aren't trivially comparable. |

Run `sourcery` (from the relevant package folder, or `make sourcery` from the repo root) before writing tests that rely on generated mocks.

### Conventions that apply everywhere

- **`@_spi(SI_SPI)`**: any public declaration meant only for use across Spark's own repositories (not by consumers of the design system) must carry this attribute.
- **Testing framework**: use **Swift Testing** by default. The exceptions that still use **XCTest** are snapshot tests, view models, and use cases that call other use cases.
- **Deprecated code**: never edit a `XXXDeprecated.swift` file or anything under a `Deprecated/` folder unless explicitly asked to deprecate something.
- **Switch-returning functions**: prefer `return switch x { case .a: "..." }` over a `return` inside every case.
- Use the matching skill (`spark-component-enum`, `spark-component-model`, `spark-component-token`, `spark-component-environment`, `spark-component-use-case`, `spark-component-view-model`, `spark-component-view`, `spark-component-accessibility-identifier`, `spark-component-constants`, `spark-component-documentation`, `spark-component-snapshots-testing`) when creating or updating any of the folders above — each one encodes the exact rules and templates. See `docs/CLAUDE_SKILLS.md` for the full list.

## Component Testing

Every component has two Tests/ subfolders: `UnitTests/` and `SnapshotTests/`.

### Unit Tests

`Tests/UnitTests/` mirrors `Sources/Core/` one-to-one — `Sources/Core/Enum/Intent.swift` is tested by `Tests/UnitTests/Enum/IntentTests.swift` for example.

- **Framework**: [Swift Testing](https://developer.apple.com/documentation/testing) (`import Testing`, `@Suite`, `@Test`, `#expect`) is the default. The exceptions that still use **XCTest** are ViewModel tests and UseCase tests where the use case calls another use case.
- **Standard imports**: `SparkComponentXXX`, `SparkCommon`, `SparkTheming`, `@testable import SparkComponentXXX`, `@_spi(SI_SPI) @testable import SparkComponentXXXTesting`, `Testing`.
- **Mocks** come from three `Testing` products, imported as needed: the component's own `SparkComponentXXXTesting`, `SparkCommonTesting`, and `SparkThemingTesting` (e.g. `ThemeGeneratedMock.mocked()` / `.mocked2()`, `ColorTokenGeneratedMock.random()`). All are Sourcery-generated — run `sourcery` (or `make sourcery`) first so they exist.
- **What each folder typically asserts**:
  - **Token**: `init(theme:)` sets every property from the theme (or from a fixed constant for a non-theme category), plus `Equatable` true/false using `mocked()` vs `mocked2()`.
  - **Model** / **Enum**: default values, and equality/inequality when properties differ.
  - **UseCase**: with `// sourcery: AutoMockable, AutoMockTest`, Sourcery generates a default-behavior test for the mock automatically, in addition to any hand-written tests for the real implementation.
  - **ViewModel** (XCTest, `// sourcery: AutoPublisherTest, AutoViewModelStub`): asserts that each `@Published private(set)` property updates correctly once its backing use case runs.

### Snapshot Tests

`Tests/SnapshotTests/` uses **XCTest** with [swift-snapshot-testing](https://github.com/pointfreeco/swift-snapshot-testing) — an explicit exception to the Swift Testing default. For a component `XXX`, the folder looks like:

```
Tests/SnapshotTests/
├── .__snapshots__/                       — recorded reference images (hidden folder)
│   ├── SparkXXXSnapshotTests/            — one subfolder per XCTestCase class
│   └── SparkUIXXXSnapshotTests/
└── Strategy/                             — "scenarios": a `CaseIterable` enum, each case producing one or more configurations
    │   ├── XXXConfigurationSnapshotTests.swift  — "configuration": every customizable variable (intent, size, variant, ...)
    │   └── XXXScenarioSnapshotTests.swift 
└── View/ 
    ├── SparkXXXSnapshotTests.swift        — SwiftUI XCTestCase, iterates every scenario × configuration
    └── SparkUIXXXSnapshotTests.swift      — the UIKit equivalent
```

- **Configuration**: a `struct` holding every property the component can be configured with, plus the display/content size modes to snapshot (`ComponentSnapshotTestConstants.Modes`/`.Sizes`).
- **Scenarios**: a `CaseIterable` enum where each case returns the configurations that exercise it. One case is always `.documentation` (`isDocumentation`) — its rendered images are copied into `Sources/Core/Documentation.docc/Resources` and referenced from `Documentation.md`'s "Rendering" section, so the DocC reference and the snapshot suite stay in sync.
- **Test cases**: `SparkXXXSnapshotTests`/`SparkUIXXXSnapshotTests` are `final class`es (inheriting `SwiftUIComponentSnapshotTestCase`/its UIKit equivalent from `SparkCommonSnapshotTesting`) that loop over every scenario's configurations and assert a snapshot for each.
- **Mocks/helpers**: `SparkCommonSnapshotTesting` (shared base test cases, constants) and, for theme values, `SparkTheme`/`SparkTheming`.
- **Regenerating baselines**: `make clear-snapshots` wipes every `.__snapshots__` folder's contents; re-running the tests re-records them. Always review the diff before committing new baselines — a passing re-record isn't the same as an intentional visual change.

## Theming Architecture

Theming lives in `Modules/Theming` (`SparkTheming`) and is the foundation every component's `Token` folder builds on.

### The `Theme` protocol

```swift
public protocol Theme: Hashable, Equatable {
    var border: any Border { get }
    var colors: any Colors { get }
    var elevation: any Elevation { get }
    var layout: any Layout { get }
    var typography: any Typography { get }
    var dims: any Dims { get }
}
```

A `Theme` is just a bag of six category protocols. Each category is itself a protocol (`Colors`, `Border`, `Elevation`, `Layout`, `Typography`, `Dims`), organized under `Sources/Core/Content/<Category>/`, and further broken down into semantic groups where it makes sense — e.g. `Colors` exposes `main`, `support`, `accent`, `base`, `feedback`, `states`, `ai`, `focus`, `new`, `business`, `service`.

### The role of Tokens

The *leaf* values of every category are exposed through a **Token** protocol rather than a raw platform type — for example `ColorToken`:

```swift
public protocol ColorToken: Hashable, Equatable {
    var uiColor: UIColor { get }
    var color: Color { get }
}
```

A token wraps both the UIKit and SwiftUI representation of a single design value behind one semantic type. This is what makes it possible to:
- Support both UI frameworks from the same theme, without every component branching on which one it's in.
- Swap themes at runtime (a token is resolved lazily from `any Theme`, not baked into a constant).
- Mock theme values in tests (`// sourcery: AutoMockable` on every category and token protocol, e.g. `ThemeGeneratedMock`, `ColorTokenGeneratedMock`).

`Modules/Theming` ships the concrete "Spark" implementation of every protocol (`ThemeDefault`, `ColorsDefault`, ...) as well as `SparkThemingTesting` (public mocks) — consumers can also implement `Theme` themselves to plug in a fully custom brand theme (see `Demo`'s `DemoTheme`/`MyThemes` customization example).

### From Theme to component Token

A component never talks to `any Theme` directly from its views. Instead, its own `Sources/Core/Token/XXXToken.swift` (see [Component Architecture](#component-architecture) above) takes a `theme: any Theme` and derives exactly the values that component needs, grouped into its own categories:

```swift
public struct ChipToken: Equatable {
    public let border: Border      // derived from theme.border
    public let size = Size()       // fixed constant, no theme needed
    public let typography: Typography // derived from theme.typography

    public init(theme: any Theme) {
        self.border = .init(theme: theme)
        self.typography = .init(theme: theme)
    }
}
```

This is the boundary between the generic theming system and a specific component: `Theming` defines *what a theme can express*, and each component's `Token` decides *which of it, and how, that component uses*.

## Resources (Iconography)

`Resources/` (`SparkResources`) hosts the Spark iconography: the `Iconography.xcassets` catalog (`Global` and `Criteria` icon sets), a generated `ImageResource` extension exposing every icon as a static property (`ImageResource.Spark`, `ImageResource.SparkCriteria`), and `Image(spark:)`/`UIImage(spark:)` convenience initializers.

The icons themselves come from [leboncoin/spark-tokens](https://github.com/leboncoin/spark-tokens); updates there automatically open a pull request on this repository (see the `🎨 PR icon updates` workflow) that regenerates the codebase via `.script/generate-iconography-codebase.swift`. See `Resources/Sources/Core/Documentation.docc/Documentation.md` for full usage details.

## Demo App

`Demo/` (`SparkDemo`) is a runnable showcase of every component and the theming system, built around `MainView` (SwiftUI/UIKit/Icons/Other tabs) and configured via `DemoConfiguration`. A `.app` build is generated every night from `main` by the `nightly-demo-app` GitHub Action. See `Demo/Sources/Core/Documentation.docc/Documentation.md` for the full setup and customization guide.
